# App CI delivery (implement → bump → push → verify release)

## When to Use
- User asks to ship/release an app update, bump an app version, or "build a new APK" via GitHub Actions.
- User reports a bug in a released build and the repo auto-builds on push.
- Need to verify whether a CI run / release / downloadable artifact actually succeeded.

Standard loop for repos whose GitHub Actions workflow builds and auto-releases on every push to main (e.g. Flutter APK workflows). Default assumption: direct push to main, no PR.

## Delivery loop
1. Clone with PAT: `git clone https://x-access-token:$TOKEN@github.com/OWNER/REPO.git`. The token usually lives in a chmod-600 file — read it into a var, never echo it into chat.
2. Implement changes; keep edits focused and review them before pushing (no local Flutter toolchain may exist — CI success IS the compile check, so self-review the Dart carefully).
3. Bump version. Flutter convention: `version: X.Y.Z+BUILD` in pubspec.yaml. Check the workflow's tag logic to know what the release tag will be (e.g. `v0.0.4+1`).
4. Commit with a subject like `vX.Y.Z: summary of change` and push to main.
5. Find the run: `GET /repos/OWNER/REPO/actions/runs?head_sha=<sha>`. Run registration lags 10–60s after push — poll a few times before concluding it failed to start.
6. Poll status every ~30s. Foreground terminal calls cap at 600s — run polling in bounded chunks (≤16 × 30s per call) and resume in the next call if still `in_progress`.
7. Verify the release: `GET /releases` → expected tag exists with the asset listed; then `curl -sIL <asset_url>` → expect 302 → 200 with `application/vnd.android.package-archive`. For content/data fixes, verify the fix is INSIDE the artifact, not just the version number: download the APK, unzip it, and read the bundled file (Flutter path is `assets/flutter_assets/assets/<path>`, e.g. query the bundled `.db` with sqlite3) before telling the user it's fixed.
8. Report to the user in their language (Persian for this user): what shipped, commit sha, build status, direct download link, and any known caveats.

## ⛔ Build gating (USER PREFERENCE — hard rule)
- Do NOT trigger a build/release for small fixes without asking, unless the user pre-authorized it ("بیلد بزن", or is offline expecting autonomous completion) or several fixes have batched up.
- Code commits/pushes are always safe; the *release* is the gated step.
- When in doubt: land the code, list pending changes, ask "بیلد بزنم؟" and wait.

### Autonomy within a delegated task (USER PREFERENCE — first-class rule)
- Once the user delegates a task with clear goals, do NOT pause to ask permission for sub-steps or present "shall I do X or Y?" menus mid-task. He stated it twice and got frustrated ("گفتم ازم سوال نپرس و انجام بده"). Decide, execute end-to-end, report results in Persian when done.
- Clarifying questions are only legitimate for genuinely blocking unknowns (missing file, contradictory requirement) — never for "may I proceed with the obvious next step".
- Content sourcing: for content-app DB work, the USER supplies the sources himself ("منابع رو خودم پیدا می‌کنم"). Do not web-search for content unless he explicitly orders it; if rate-limited mid-search, stop searching and wait for his material.

### Non-release pushes that trip the auto-builder
A push of DB/content changes to main still triggers a push-triggered build workflow. If the user has gated builds:
1. After pushing, immediately check `GET /actions/runs?per_page=1` — a run for the new sha likely started within seconds.
2. Cancel it: `POST /actions/runs/<run_id>/cancel` (202).
3. Disable the workflow so later non-release pushes don't re-trigger: list workflows (`GET /actions/workflows`) → `PUT /actions/workflows/<id>/disable` (204). Re-enable the same way (`/enable`) as the first step of the next approved release.
This dance ran twice in the Hoda repo (after DB-only commits). Current state (post-v0.1.0): the workflow was re-enabled and the release dispatched manually — it is ON, so the NEXT non-release push (DB edit, docs) will auto-build again and must be cancelled/disabled immediately if the user hasn't ordered a release.

## Pitfalls
- **Flutter: new asset invisible at runtime.** Any file added under `assets/` MUST be declared in pubspec.yaml `flutter: assets:`. Undeclared → `Image.asset` fails → errorBuilder placeholder renders instead (the user literally sees the fallback). Always re-check pubspec after adding any asset.
- Make Flutter errorBuilder fallbacks brand-appropriate (monogram/text), never joke icons — an `Icons.flight` fallback looked like an airplane-mode bug to the user.
- **Security scanner blocks:** `curl | python3` pipes and inline heredoc scripts get flagged/blocked. Pattern that works: `curl -o /tmp/x.json` then parse the file with python; write multi-step logic to a `.sh` via write_file and execute it.
- Chunked polling only — a single polling loop longer than the tool timeout dies with partial results.
- Verify the release asset's download URL (HTTP 200 after redirect), not just the release object's existence.
- When the user reports a visual bug ("logo wrong"), first reproduce the cause in code (e.g. grep pubspec for the asset) before changing anything.

## Integrating externally-edited source zips (AI handoff)
When the user edits the codebase with another AI (e.g. Claude) and sends back a zip, proven workflow (done twice):
1. Extract to /tmp — NEVER copy the zip over the repo wholesale. Outside zips typically lack `.github/`, `.gitignore`, `android/.gitignore`; overwriting would silently delete the CI build workflow.
2. Diff every file; copy only genuinely changed ones. Shared files (theme, main, database_helper, models, assets) are often byte-identical — verify with md5. **Watch for repo-owned infra regressing inside the zip**: the zip is a snapshot of the other AI's workspace, so if that workspace predates your repo-side changes, its copies of YOUR files (build.gradle signing config, proguard-rules.pro dontwarns, workflow) are older. Real case: the v0.0.9 zip's build.gradle still had `signingConfig = signingConfigs.debug` and its proguard-rules.pro was missing the play.core dontwarn — copying either would have silently broken stable signing / the R8 fix. Rule: never copy the zip's `build.gradle` / `proguard-rules.pro` / `.github` wholesale; keep the repo version and re-apply only genuinely new rules from the zip on top.
3. Code-review ALL foreign Dart line by line before pushing. AI zips have shipped compile-breaking typos (`MainISAis.min`); with no local SDK, CI is the only compiler and a typo burns a build cycle plus a failed run the user can see. Cheap syntax gate that works: a comment-aware balance scan — strip `//` and block comments AND string literals first (Persian text/comments contain apostrophes that cause false positives), then assert `{`==`}` and `(`==`)` over every `*.dart`. Ran over v0.0.7's 24-file refactor: all clean, build passed first try.
4. The zip's pubspec `version:` is *often* stale (v0.0.5 was; v0.0.7 arrived already bumped) — verify and bump as needed rather than blindly overwriting the user's number.
5. **Same-minor re-ships** (user sends `0.0.9.1` for the `0.0.9` you just released): the zip's pubspec usually still carries the old build number — bump the build (`+1`→`+2`), keep the release title = short version, and DELETE the superseded release that shares the title (`DELETE /releases/<id>`, tag `v0.0.9+1`) so exactly one release + one APK per version remains.
6. When packaging the repo back INTO a source zip for the external AI, exclude secrets and build artifacts: `-x "<repo>/.git/*" "<repo>/build/*" "<repo>/.dart_tool/*" "<repo>/android/app/*.jks" "<repo>/android/key.properties"` — the signing keystore must never leave the machine (its password lives in a separate chmod-600 file). Tell the user the exclusions are deliberate; infra files (`.github/`, signing config, dontwarns) get re-applied at merge time anyway.
7. Build gating still applies: if the user said "منتشر کن / release this", build; otherwise land the merge and ask.

## Stable signing + release naming (in-place updates)
Users hate uninstalling the old app before installing the new build. Root cause: builds signed with the *debug* keystore get a different signature every machine/run → Android refuses an update install. Fix pattern (worked end-to-end):
1. Generate one upload keystore (needs a JVM: `apt-get install default-jre-headless` provides keytool): `keytool -genkeypair -keystore hoda-upload.jks -alias hoda-upload -keyalg RSA -keysize 2048 -validity 36500 -dname "CN=<App> ..."`. Keep a local chmod-600 copy + separate password file, and back both up.
2. Store it as GitHub **Actions secrets** (encrypted with the repo's public key — `GET /actions/secrets/public-key`, seal with PyNaCl `SealedBox`, `PUT /actions/secrets/<NAME>`): one secret holding the base64 of the .jks, one holding the password.
3. Workflow decodes them into `android/app/hoda-upload.jks` + `android/key.properties` at build time; `build.gradle` loads key.properties and sets `signingConfig` from it (debug fallback when absent, so local dev still builds). Verify by downloading the released APK, unzipping `META-INF/CERT.RSA`, and `keytool -printcert` — owner must match your keystore.
4. One-time migration cost: builds released *before* the switch were debug-signed, so installing the first stably-signed build still requires one final uninstall. Say this explicitly to the user.

Release naming (user preference): release **title** = plain short version (`0.0.8`), not the tag with build number (`v0.0.8+1`); APK asset renamed to `<app>-v<short>.apk` (copy the flutter output before upload). Fixing old titles is cheap via `PATCH /releases/<id> {'name': ...}`.

**User checks the releases page — keep it clean.** He noticed the duplicate `app-release.apk` sitting next to `hoda-v0.0.8.apk` after the re-release and told us to remove it. Rules: a re-release that re-uses a tag ADDS the new asset alongside the old one (old upload survives) — the workflow's `gh release upload --clobber` only overwrites when the re-push actually runs, so after any manual re-release, check `GET /releases` and DELETE (`DELETE /releases/assets/<id>`) stale assets so exactly one APK remains. Asset-name consistency was retro-applied too: every historical `app-release.apk` renamed to `hoda-v<short>.apk` via `PATCH /releases/assets/<id> {'name': ...}` (cheap, old download URLs break — acceptable; no README referenced them, but grep README for `releases/download` before renaming).

## Non-Flutter Android sources → NEW repo (games/apps from other AIs)

The user also ships complete Android projects (games) written by other AIs and asks to build + publish them as a **new GitHub repo** «مثل هُدا». Pipeline that worked (pahpad-shahed v1.0.0, native Kotlin + Canvas):

1. **Inventory first, then pick the buildable zip.** AI-generated "game source" often arrives in two flavors: a Unity project (`.unity` scene pipelines, `ProjectSettings/ProjectVersion.txt`, scenes generated by an Editor tool — NOT CI-buildable without a Unity license) and a native Android/Kotlin project (plain `build.gradle.kts` + `AndroidManifest.xml`). When the user says «هر کدوم بهتره», build the native one and say why.
2. **Create the repo via API**: `POST /user/repos {'name', 'description', 'private': false}` (the dnh-bit token has repo-create scope). `git init` in the cleaned source dir, commit with the dnh-bit identity, push with the token remote.
3. **Gradle wrapper absent is fine**: AI zips omit the binary `gradle-wrapper.jar`. Do NOT require `./gradlew` — use `gradle/actions/setup-gradle@v3` with an explicit `gradle-version` (below) and call `gradle` directly.
4. **CRITICAL — runner Gradle vs AGP mismatch**: ubuntu-latest runners ship **Gradle 9.x**, which breaks AGP 8.2.x with the misleading error `Cannot mutate the dependencies of configuration ':app:releaseCompileClasspath' after the configuration was resolved` (it appears even after removing the code that looked responsible). Fix: pin Gradle in the workflow via setup-gradle `gradle-version: '8.2'` (match the project's `gradle-wrapper.properties`). One failed CI cycle taught this; the error text points at resources, not the version.
5. **`resourceConfigurations += listOf("fa")` in Kotlin DSL + AGP 8.2** triggers that same config-mutation error; `androidResources { localeFilters }` doesn't exist until a newer AGP (`Unresolved reference 'localeFilters'`). Locale filtering is a size optimization — just delete it rather than fighting the DSL.
6. **Signing a non-Flutter Kotlin-DSL app with repo secrets**: write `app/keystore.properties` from secrets in CI; in `build.gradle.kts` put `import java.util.Properties` / `import java.io.FileInputStream` at the very top, then inside `android {}` a guarded `if (keystorePropsFile.exists()) { signingConfigs { create("upload") … } buildTypes { release { signingConfig = … } } }`. Reusing the existing org keystore (same base64 + password secrets, names like `<APP>_UPLOAD_KEYSTORE_B64` / `<APP>_KEYSTORE_PASSWORD`, sealed via PyNaCl against `GET /actions/secrets/public-key`) gives in-place updates across builds and apps.
7. **Verify a v2-only signature correctly**: an AGP-signed release APK may have NO `META-INF/CERT.RSA` — the v2 signing scheme stores the block between zip entries. `unzip`-based cert checks report "unsigned" for perfectly valid APKs. Correct check: read the file bytes and test `b'APK Sig Block 42' in data` (v2 scheme is valid for everything the app supports if minSdk ≥ 24 / Android 7+).
8. **Tiny APKs are plausible**: a pure-Canvas Kotlin game with zero external deps + R8 minify is ~180 KB. Verify the content made it in by scanning the dex for Persian UTF-8 substrings (`re.findall(rb'(?:[\xd8\xdb][\x80-\xbf]){3,}', dex)` → hundreds of hits) instead of judging by size. `find app/build/outputs -name "*.apk"` (glob, not a hardcoded name) for the rename step — output naming varies with signing config.
9. **Keep the repo as the single source of truth when updating**: extract user zips to a sibling dir, apply edits there, but before syncing INTO the repo dir remember the zip tree is pristine — a careless `cp -r zip/. repo/` **overwrites repo-side infra** (real case: the v0.0.2 sync clobbered the signing block out of `build.gradle.kts`; CI happily published an unsigned APK because `keystore.properties` was written but never read). After any bulk copy, `grep keystorePropsFile app/build.gradle.kts` before pushing, and treat a build log line `app-release-unsigned.apk` as a red flag to stop the release. `cp -r` (no rsync on this box) + explicit post-copy grep is the working pattern.
9b. **External-AI zips carry their own CI workflow — never adopt it.** Their `build.yml` typically only uploads a debug artifact and explicitly does not publish releases. Keep the repo's signed-release workflow; sync its hardcoded `tag_name`/release `name:`/APK filename to the new version in the same commit as the version bump. Also triage the zip's non-source dirs (`art-source/`, `preview/`, `tools/`, `checks/`, delivery-note .md files): they don't affect the build — ask the user whether they belong in the repo (for pahpad-shahed 0.0.3 he said yes to art-source; the 8MB-zip-vs-4MB-repo question he asked was exactly this split).
10. **The workflow's `tag_name` is hardcoded per release** (softprops/action-gh-release has no version variable in this skeleton) — update `tag_name`, release `name:`, and the APK filename in the same commit as the version bump, and DELETE the previous release+tag (`DELETE /releases/{id}`, then `git push origin :refs/tags/<old>`) when renumbering (v1.0.0 → v0.0.2), or the new APK lands on the stale tag and deleting it loses the asset.
10b. **RELEASE ARCHIVE RULE (USER, 2026-09-07, applies to ALL repos — same as Hoda): never delete, PATCH, re-tag, or re-label an old release.** Ship the next version as its own normal release; previous releases stay exactly as published (no retroactive prerelease marks, no body edits, «دقیقا مثل نرم افزار هدا عمل کن و هر بار نسخه بعدی رو بساز و کاری به نسخه های قبل نداشته باش»). Deleting a release is only for duplicate-title cleanup when rebuilding the SAME version after a correction. If a release was already deleted, it can be reconstructed: recreate the tag (`POST /git/refs`) at the original build commit and re-upload the APK kept in /tmp — downloaded release APKs are the only archive, so keep them until superseded.
10c. **Retracting a whole bad version** (user: «افتضاحه… 0.0.6 رو حذف کن», pahpad-shahed): `DELETE /releases/<id>` + delete the remote tag, then `git reset --hard <last-good-commit>` + force-push. The force-push auto-triggers CI — **cancel that run immediately** (`POST /actions/runs/<id>/cancel`, confirm `completed/cancelled`) or the rebuild re-publishes onto the previous version's still-existing tag and touches a release that must stay untouched. End state: repo HEAD == last-good commit, bad tag/release gone, all older releases byte-identical.
11. **No local Kotlin toolchain → brace/paren balance checks are the pre-push gate**, but they do NOT catch Kotlin-specific issues like duplicate identical imports (`Conflicting import, imported name 'Paint' is ambiguous` — two `import android.graphics.Paint` lines). Dedupe imports mechanically after scripted insertions (a script that prepends an import can double it if one already exists); grep the failed CI log for `e: file:` lines — they carry file:line for each compile error.

### User-driven iteration on a shipped game (v0.0.2 pattern)
The user judges the first build harshly («خیلی ابتداییه») and renumbers versions himself (called the shipped 1.0.0 «ورژن 0.0.1 بود») — treat his numbering as canonical, ship the next as 0.0.2. His two complaints decoded into concrete fixes by **reading the source and computing the real numbers**: «سوخت کمه، بازی قابل تموم کردن نیست» turned out to be arithmetic — base range 500 m vs level 1-1 distance 600 m, so mission one was unwinnable before any upgrade; fix = raise range anchors (500/1000/2000 → 900/1600/2600), exclude wind displacement from fuel burn (it moved the drone but was charged as distance), soften boost 1.6×→1.25×, add 15% maneuver headroom (`fuelLeft = maxRange * 1.15f`). «عکس دار بشه» (drones, regions) = PIL-generated asset pack, see `references/game-asset-generation.md` for the generator recipe + runtime wiring (assets/ bundles unregistered in native Android, post-flush billboard sprites, ground-shadow trick).

**Iteration 2 (v0.0.3) taught: a partial numeric fix can still leave late-game unwinnable** — the 0.0.2 anchors (900/1600/2600) covered ch1 but ch2+ levels (1000–2200 m) still exceeded base fuel, and the user reported it precisely («فقط دو مرحله آموزشی اول اوکی بود»). The durable pattern is **guaranteed reachability**: `fuelLeft = Math.max(maxRange, level.distance * 1.45f) * 1.15f` — scale fuel to the mission, don't chase per-level anchor tuning. When the user reports "can't reach X", compute the full distance/fuel table across ALL levels, not just the first ones. Full v0.0.3 log (external-AI graphics pass, workflow-adoption trap, bare-`max` Kotlin trap, release-archive rule) in `references/pahpad-shahed-case.md`.

### Ingesting a returned external-AI zip (standing checklist — snapshot drift fires EVERY time)
External AI zips are built from **the zip you sent the user, not repo HEAD**. Every repo-side fix made after that zip was sent is silently absent from the returned source, even when the AI's delivery note claims protected files are «بایت‌به‌بایت ثابت» (this false claim has now appeared on three consecutive ingests). Standing ingest checklist:
1. `diff -rq` the zip tree against the repo (excluding dev-artifact dirs) and **`cmp` every file you personally changed since sending** — re-apply your fixes if missing. For pahpad-shahed the standing repo-side fixes are: (a) fuel anchors `anchored(level, 1200f, 1900f, 2800f)` in DroneModels.kt, (b) the guaranteed-reachability line at the mission-reset site in Mission.kt (see below), (c) `assets/fonts/Vazirmatn-Regular.ttf` (copy from the Hoda repo, OFL).
2. Re-run the standing checks regardless of the note: `grep keystorePropsFile app/build.gradle.kts` (signing), `grep -rn '"<old-version>"' app/src/main/java` (hardcoded UI version strings drift from gradle at every bump), brace-balance scan, import-dedupe scan.
3. Then the normal merge: keep the repo workflow + gradle infra, sync their genuinely-new source, bump version in gradle AND the workflow tag in one commit.
4. **Scripted fix re-application pitfall**: a blind regex `s/fuelLeft = [^\n]+/new/` hits the property *declaration* (`var fuelLeft = 0f`) instead of the reset site. Place the guarantee expression at the mission-reset location (where throttle/boost are re-initialized), keep the declaration `= 0f`, and after ANY scripted edit `grep -n <symbol>` and read surrounding lines before pushing.
5. Keep the user's own version numbering canonical — he renumbers versions himself («ورژن 0.0.1 بود» for the shipped 1.0.0); the next release takes HIS next number, not the zip's.
A domain-prompt with immutable invariants gets high compliance (the AI kept versionCode/gradle/deps untouched as ordered) — the failure mode is not disobedience, it is the stale base.

## R8 / ProGuard traps (release-only failures)
- **flutter_local_notifications + Gson**: R8 strips generic signatures → `PlatformException(error, Missing type parameter.)` from `loadScheduledNotifications()` on *release* APKs only (debug isn't shrunk) — every `cancel()`/`zonedSchedule()` throws. Fix: proguard-rules.pro with `-keepattributes Signature,*Annotation*,InnerClasses,EnclosingMethod`, keep rules for `com.dexterous.flutterlocalnotifications.**` + Gson `TypeToken` subclasses, wired via `proguardFiles ... 'proguard-rules.pro'` in buildTypes.release.
- **R8 "Missing class" aborts the build**: e.g. `com.google.android.play.core.splitcompat.SplitCompatApplication` referenced by `FlutterPlayStoreSplitApplication` though split delivery is unused → add `-dontwarn com.google.android.play.core.**`. Cost one failed CI run to discover.
- **`shrinkResources false`** on purpose: resource shrinking has broken font/raw-asset lookups (Amiri/Vazirmatn) before.
- Debug builds don't run R8 — a release-only crash with a healthy debug run is a ProGuard/R8 signature smell first.

## Real notifications on Flutter/Android (flutter_local_notifications v17)
A "notification settings" UI that only writes SharedPreferences = no engine. Symptom the user reports: "never asks permission, toggle does nothing" — the fix is a real engine, not UI tweaks. Recipe in hoda-case.md; API traps that cost one failed CI build:
- `tzdata.initializeTimeZones()` — capital Z. `initializeTimezones()` = "Method not found".
- `zonedSchedule` in fln 17.x REQUIRES `uiLocalNotificationDateInterpretation:` (e.g. `UILocalNotificationDateInterpretation.absoluteTime`).
- `android/app/build.gradle` needs `minSdk = 23` (flutter default 21 is too low for fln v17).
- Manifest needs `POST_NOTIFICATIONS`, `RECEIVE_BOOT_COMPLETED`, `SCHEDULE_EXACT_ALARM` (+ `VIBRATE`).
- **Scheduled notification never fires even though a manual test `show()` works?** The plugin's own manifest only declares permissions — the app manifest MUST also declare the plugin receivers: `com.dexterous.flutterlocalnotifications.ScheduledNotificationReceiver`, `ScheduledNotificationBootReceiver` (intent-filter: BOOT_COMPLETED, MY_PACKAGE_REPLACED, QUICKBOOT_POWERON) and `ActionBroadcastReceiver`, all `android:exported="false"`. Without them AlarmManager fires into the void. (v0.0.7 fix by Claude.)
- Exact alarms: `SCHEDULE_EXACT_ALARM` is default-granted but revocable on Android 13, user-granted on Android 14+ — code should check `android.requestExactAlarmsPermission()` and fall back to `AndroidScheduleMode.inexactAllowWhileIdle`. Do NOT declare `USE_EXACT_ALARM` (Play-restricted, non-revocable). Re-arm on app start (`restoreSchedule()`) since AlarmManager drops alarms after reboot/app-update/force-stop.
- Repo `pubspec.lock` may predate the new deps — CI `pub get` resolves it; don't hand-edit the lock.
- APK size jumps (e.g. 23→50 MB) when fln + permission_handler + timezone land — expected, mention it to the user.
- Failing CI logs: runs API → jobs API → job id → `GET .../actions/jobs/<id>/logs` → save to /tmp/build.log and read the "Build APK" step errors.
- **RTL notifications on English-locale devices** (v0.0.9.1): SystemUI lays out notification text by the *device* locale, so Persian/Arabic on an English phone renders as a neutral run in an LTR paragraph — punctuation and digits jump to the wrong side. Fix = Unicode bidi embedding pair `U+202B` (RLE) … `U+202C` (PDF) around every visible string, with three rules: (1) each `\\n`-separated body line gets its OWN pair (an embedding does not survive a paragraph break); (2) control chars go INSIDE the HTML tags (`<b>\\u202B…\\u202C</b>`) so they survive markup stripping; (3) wrap all four slots — title/contentTitle, every body line, summary, and the heads-up ticker. Subtext is plain text (no HTML parsing) → wrap literally.

## Growing a content DB (user-supplied source documents)
Full loop moved to `references/content-db-ingestion.md`. Essentials: parse only `doc.tables` (never the prose — the user says so), validate numbering continuity across multi-table docs, dedupe on normalized Arabic BEFORE insert, verify all N rows covered + integrity_check, and bump `dbContentVersion` whenever the bundled DB schema changes.
